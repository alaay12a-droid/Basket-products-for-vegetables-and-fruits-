# السلة للتاجر — تطبيق مستقل

هذا تطبيق جديد مستقل في `artifacts/basket-merchant`، بمعرّف أندرويد مستقل `com.basket.merchant`. لا يستبدل معرّف تطبيق العميل `com.basket.products`، ولا يغيّر ملفات واجهات العميل أو المندوب أو الداشبورد.

## الحالة الحالية بوضوح

- واجهة عربية RTL مناسبة للجوال والأجهزة اللوحية، مع صفحات الطلبات والأرشيف والأصناف والمندوبين والمحادثات والساعات والإشعارات والمساعدة والشروحات والإعدادات.
- معاينة الواجهة دون اتصال متاحة من شاشة الدخول. جميع الإجراءات فيها معطلة ولا توجد طلبات تجريبية تُعرض كأنها طلبات متجر حقيقية.
- خدمة مستقلة، جلسة تاجر خاصة قابلة للإلغاء، عزل طلبات الموظف بحسب فروعه، أوامر لها معرّف يمنع تكرار التنفيذ، WebSocket مع إعادة الاتصال.
- تكامل أندرويد أصلي للطباعة العربية كصورة نقطية، لا عبر طباعة المتصفح، وQR محلي دون إرسال بيانات الفاتورة إلى موقع خارجي.
- تم تجميع APK مستقل بالإصدار `1.0` ومعرّف `com.basket.merchant` للتثبيت المباشر والاختبار، والتحقق من سلامة الملف وتوقيعه. **لم يُختبر على جهاز فعلي ولم يتم إثبات توافق طابعة V3H المرفقة**.
- الملف الناتج نسخة `Debug` موقّعة للاختبار، وليس إصدارًا تجاريًا بمفتاح توقيع نهائي. الإصدار التجاري يحتاج مفتاحًا خاصًا محفوظًا بأمان؛ لا تفترض إمكانية تحديث نسخة الاختبار بتوقيع مختلف دون إزالة النسخة القديمة.
- الاتصال يحتاج تفعيلًا صريحًا؛ تم تفعيله في إعدادات هذا المشروع بعد موافقة صاحبه والتحقق من قاعدة السلة وتوقيع API، مع تثبيت الجداول التسعة الإضافية فقط. لا توجد ترحيلات تلقائية عند التشغيل أو البناء، ولم تُنشأ طلبات تجريبية.
- الرابط الدائم لخدمة التاجر يحتاج نشر النسخة الحالية والتحقق من `/basket-merchant/api/merchant/status` قبل بناء APK. لا يكفي نجاح المعاينة للحكم بأن خدمة الإنترنت منشورة.

## حدود مهمة قبل التشغيل التجاري

1. صورة «لمحة عن الجهاز» أكدت أن الجهاز V3H يعمل بـSUNMI OS 4.0.38. المكتبة الرسمية `com.sunmi:printerlibrary:1.0.24` مدمجة بالفعل. الجسر يفحص خدمة SUNMI عند تشغيل التطبيق، ويختار الطابعة المدمجة تلقائيًا عند نجاح الاتصال الفعلي، مع ورق 58 مم لـV3H. اسم الموديل وحده لا يكفي لأجهزة أخرى. لم تُختبر ورقة مطبوعة على الجهاز الفعلي من هذه النسخة بعد.
   - تبقى خيارات ESC/POS عبر الشبكة والبلوتوث متاحة ولا يستبدلها الاكتشاف التلقائي.
   - تحفظ خيارات اتصال الطابعة محليًا لكل كاشير؛ اختيار «بدون طابعة» وحفظه يوقف الاختيار التلقائي على ذلك الجهاز.
   - زر «طباعة تجريبية» يطبع نسخة واحدة من سطر عربي ورقم `1234567890`، بلا إنشاء طلب أو إرسال إشعار. العربية تُرسم كصورة قبل إرسالها للطابعة.
2. طابعات ESC/POS الشبكية والبلوتوثية تدعم الأجهزة المتوافقة، وليست ضمانًا بأن كل طابعة مدمجة متاحة بهذه الطريقة. اربط الطابعة Bluetooth من إعدادات الجهاز أولًا ثم أدخل MAC، أو أدخل IP المحلي والمنفذ عادة 9100.
3. إعداد 58 أو 80 مم لا يحوّل طابعة 58 مم إلى طابعة 80 مم. اختر المقاس الفيزيائي الصحيح.
4. خدمة متابعة الطلبات بالخلفية مرئية في إشعارات أندرويد. إيقاف التطبيق إجباريًا، رفض الإشعارات، توفير البطارية، انقطاع الشبكة وقيود الشركة قد توقف المتابعة. Android 15 يفرض حدودًا زمنية على خدمات `dataSync`؛ لا نَعِد باستقبال 24/7 على كل جهاز. تشغيل تجاري موثوق عند إيقاف التطبيق يحتاج إعداد FCM خاصًا بهذا التطبيق واختباره، وليس نسخ إعدادات تطبيق العميل أو المندوب.
5. قبول الاسترداد في هذه الواجهة **تسجيل قرار إداري فقط**؛ لا يتصل ببوابة الدفع ولا يعني أن المبلغ أُعيد. يجب تسوية المبلغ بالآلية المالية المعتمدة.
6. بيانات الأصناف والمندوبين والطلبات تُشارك النظام الحالي عمدًا بعد التفعيل. تعديل التوفر يمر عبر API القائمة الموجودة؛ ظهور التغيير عند العميل يتبع آلية تحديث تطبيق العميل الحالية، دون تعديل تطبيقه.
7. منطق ساعات الكاشير متعدد الفترات مستقل. عند اختياره لإدارة ساعات المتجر، الخدمة تحدّث عقد `branch_hours` الحالي وفق الحالة الفعلية، ولا تعدّل كود العميل. يجب تشغيل الخدمة باستمرار حتى تنتهي مدد الإغلاق والإيقاف تلقائيًا.
8. هوية خدمة التاجر منفصلة، لكن تسجيل الدخول يستخدم حسابات المدير والموظفين الموجودة. لا تنشأ كلمة مرور أو حساب افتراضي.
9. الورقة تحتوي QR مرجع الطلب. **ليست شهادة امتثال أو QR فاتورة إلكترونية معتمدًا من ZATCA**. أي متطلبات فواتير ضريبية منظمة تحتاج مراجعة وربطًا مستقلًا.

## التفعيل الآمن على قاعدة السلة

لا تنفذ هذه الخطوات على قاعدة تحمل اسم مشروع آخر. لا تستخدم `drizzle push` أو أي أمر يعيد إنشاء الجداول الحالية.

1. ضع اتصال قاعدة السلة الخارجية الصحيح في Secret مستقل اسمه `MERCHANT_DATABASE_URL`، وراجع هوية `app_settings`، وخذ نسخة احتياطية بالطريقة المعتادة لدى مزود قاعدة البيانات. الخدمة لا تستخدم `DATABASE_URL` الخاص بـReplit ولا تستبدله؛ اتصالها مشفر مع التحقق من شهادة TLS.
   بديل وافق عليه صاحب المشروع: ضبط `MERCHANT_DATABASE_SOURCE=SCHEMA_BOOTSTRAP_DATABASE_URL` لاستخدام الاتصال الصحيح المحفوظ أصلًا، دون نسخ قيمته أو تغيير أي Secret. هذا اختيار صريح وليس fallback؛ القيمة الافتراضية تبقى `MERCHANT_DATABASE_URL`. عند نشر الخدمة يجب توفير السر المختار في بيئة النشر أيضًا.
2. راجع `server/schema.sql`: ينشئ فقط الجداول ذات البادئة `merchant_`، ويعيد استخدام جداول المستخدمين والطلبات والمندوبين والرسائل والأصناف الموجودة.
3. بعد التأكد والموافقة على الهدف، شغّل صراحةً:

   ```bash
   MERCHANT_SCHEMA_CONFIRM=BASKET_ONLY pnpm --filter @workspace/basket-merchant run db:setup
   ```

   هذا الأمر ليس ضمن أوامر `dev` أو `build` أو `start`. يفحص هوية السلة قبل الكتابة. تم تشغيله صراحة بعد موافقة صاحب المشروع والتحقق من تطابق المنتجات وقبول توقيع API.

4. اضبط `MERCHANT_CORE_API_URL` على رابط API الحالي الصحيح للسلة عبر HTTPS وينتهي بـ `/api`، وتأكد أن قاعدة خدمة التاجر وتوقيع جلساتها يطابقان هذا الـAPI، وليس مشروعًا آخر. الأوامر تمر للخادم الحالي للحفاظ على قواعد الطلبات والإشعارات وروابط المندوب؛ لا تبدأ الخدمة نسخة ثانية من خادم العميل.
   ضع نسخة من قيمة `DASHBOARD_JWT_SECRET` **الموجودة في خدمة API السلة الصحيحة على Render** في Secret خاص بالتاجر اسمه `MERCHANT_CORE_JWT_SECRET` عبر إدارة الأسرار فقط؛ لا تولّد قيمة مختلفة ولا تغيّر قيمة خدمة Render. قيمة التوقيع الموجودة في بيئة Replit لم يقبلها API السلة في الفحص، لذلك لا نستخدمها. لا تنسخ أي سر في الكود أو Git.
   بعد التحقق من قبول التوقيع وتطابق البيانات، فعّل `MERCHANT_ENABLED=true` في خدمة التاجر فقط.
5. انشر خدمة التاجر الخاصة عبر Node، وليس استضافة ملفات ثابتة فقط. تشغيلها:

   ```bash
   pnpm --filter @workspace/basket-merchant run build
   pnpm --filter @workspace/basket-merchant run start
   ```

   يضبط المشغّل `PORT` و`BASE_PATH=/basket-merchant/`. مرّر WebSocket في المسار `/basket-merchant/events`. واجهاتها تحت `/basket-merchant/api/merchant/`.
6. افتح `/basket-merchant/api/merchant/status` وتأكد من `enabled: true`. اختبر بحساب موظف لفروعه فقط قبل إعطاء صلاحيات مدير.
7. اختبر طلبًا بإذن المتجر على جهاز واحد: الاستقبال، الصوت، القبول، الطباعة، المحادثة، وتعيين مندوب. راجع سجلات الخدمة دون تسجيل الجلسات أو كلمات المرور.

## تشغيل التاجر على سيرفر Render الحالي

التاجر يبقى تطبيقًا مستقلًا، لكن سيرفره يمكن تشغيله على نفس خدمة Render التي تخدم العميل والمندوب والداش بورد:

- التطبيق: `https://basket-products-api.onrender.com/basket-merchant/`
- فحص الجاهزية: `https://basket-products-api.onrender.com/basket-merchant/api/merchant/status`
- الاتصال اللحظي: `wss://basket-products-api.onrender.com/basket-merchant/events`

أمر البناء الحالي لـ `@workspace/api-server` يبني الداش بورد وواجهة التاجر، ويُخرج وحدة خدمة التاجر المستقلة بجانب ملف السيرفر. أمر التشغيل يبقى `pnpm --filter @workspace/api-server start` وعلى نفس منفذ Render؛ لا تشغّل نسخة ثانية من API العميل.

بعد رفع الكود، اضبط في إعدادات خدمة Render، وليس داخل الشيفرة:

| المتغير | القيمة أو المطلوب |
| --- | --- |
| `MERCHANT_EMBEDDED` | `true` لتشغيل خدمة التاجر داخل سيرفر Render |
| `MERCHANT_ENABLED` | `true` بعد التأكد من صحة الاتصال والجداول الحالية |
| `MERCHANT_DATABASE_SOURCE` | `MERCHANT_DATABASE_URL` |
| `MERCHANT_DATABASE_URL` | اتصال قاعدة السلة نفسها التي يستخدمها التاجر حاليًا، مع TLS؛ لا تنشئ قاعدة جديدة |
| `MERCHANT_CORE_API_URL` | `https://basket-products-api.onrender.com/api` |
| `MERCHANT_CORE_JWT_SECRET` | نفس توقيع `DASHBOARD_JWT_SECRET` المستخدم في API السلة الحالي، عبر حقول الأسرار فقط |

لا يوجد نقل تلقائي للأسرار من Replit إلى Render. لا تُرسل كلمات المرور أو الاتصالات السرية في الدردشة أو GitHub. لا يلزم تغيير إعدادات العميل أو المندوب أو الداش بورد. هذه الخطوة لا تُنشئ جداول ولا تشغّل ترحيلًا؛ فحص الجاهزية يمنع التفعيل إذا لم تطابق القاعدة السلة أو لم توجد جداول التاجر.

تحقّق بعد نشر Render أن `/api/merchant/status` تحت مسار التاجر يرجع `enabled: true`. افحص أيضًا API العميل والداش بورد. لا تبنِ أو توزّع APK بالرابط الجديد قبل نجاح هذا الفحص؛ النسخة المثبتة القديمة تبقى على رابطها القديم حتى تثبيت APK جديد.

## بناء Preview عبر Expo/EAS

توجد إعدادات مشروع Expo مستقل للتاجر في `app.json`، وبروفايل `preview` فقط في `eas.json`. هذا بناء APK داخلي للتثبيت المباشر، وليس رفعًا لمتجر Play، ولا يحوّل التطبيق إلى React Native، ولا يجعل تشغيله داخل Expo Go ممكنًا.

يستخدم `.eas/build/preview.yml` خطوات مخصصة لبناء Capacitor بواسطة Java 21 وGradle، دون `expo prebuild` الذي قد يستبدل مشروع أندرويد الأصلي. هذه النسخة تستخدم توقيع Debug للاختبار، ولا تنشئ أو تستعمل مفاتيح التطبيقات الأخرى.

ملف `.easignore` العام يستبعد مجلدات أندرويد لتطبيقات Expo الأخرى، لذلك لا تغيّره لهذا الغرض. جهّز شجرة رفع مستقلة تحتوي التاجر والمكتبات اللازمة فقط:

```bash
# من جذر المستودع، اختر اسم مجلد جديدًا لكل تجهيز.
node artifacts/basket-merchant/scripts/prepare-eas-preview.mjs merchant-eas-next
export EAS_NO_VCS=1
export EAS_PROJECT_ROOT="$PWD/generated-artifacts/merchant-eas-next"
cd "$EAS_PROJECT_ROOT/artifacts/basket-merchant"
eas build --platform android --profile preview --non-interactive --wait
```

لا تُرفع ملفات الأسرار أو الشهادات أو العميل أو المندوب أو الداشبورد. لا تشغّل الأمر مجددًا إذا كان هناك بناء جارٍ أو في الانتظار؛ راقب صفحة البناء أولًا لتجنب محاولات مدفوعة غير لازمة. اكتمال بناء APK لا يعني أن رابط خدمة التاجر الدائم نُشر.

## بناء APK على الكمبيوتر

تحتاج Android Studio مع Android SDK 35 وJava 21، وNode وpnpm. البناء المحلي لا يحتاج Expo أو EAS ولا يتطلب رفع إصدار العميل.

1. افتح نسخة المشروع على الكمبيوتر ونفّذ من جذر المشروع:

   ```bash
   pnpm install --frozen-lockfile
   ```

2. بعد نشر خدمة التاجر والتحقق من جاهزيتها، ضع رابط خدمة التاجر الفعلي في متغير البناء `VITE_MERCHANT_SERVER_URL`. يجب أن يبدأ بـ HTTPS وينتهي بـ `/basket-merchant`، دون `/` أخيرة. الرابط إعداد عام وليس مفتاحًا سريًا.

3. ابنِ حزمة الويب المخصصة للجهاز ثم زامن Android:

   ```bash
   # ضع رابط خدمتك الفعلي بدل المثال، ولا تستخدم localhost.
   export VITE_MERCHANT_SERVER_URL="https://basket-products-api.onrender.com/basket-merchant"
   pnpm --filter @workspace/basket-merchant run build:native
   pnpm --filter @workspace/basket-merchant run android:sync
   pnpm --filter @workspace/basket-merchant run android:open
   ```

   إذا لم يوجد رابط صحيح، نسخة أندرويد تتوقف برسالة إعداد واضحة بدل الاتصال بتطبيق آخر.

4. انتظر مزامنة Gradle في Android Studio. لبناء نسخة اختبار اختر **Build → Build App Bundle(s) / APK(s) → Build APK(s)**، أو:

   ```bash
   cd artifacts/basket-merchant/android
   ./gradlew assembleDebug
   ```

5. تجد ملف الاختبار في:

   ```text
   artifacts/basket-merchant/android/app/build/outputs/apk/debug/app-debug.apk
   ```

6. انقل APK للجهاز عبر USB، وافتحه، واسمح بالتثبيت من هذا المصدر عند الطلب. هذه صلاحية تثبيت فقط؛ لا تمنح صلاحيات غير لازمة.
7. افتح التطبيق وسجّل دخول التاجر، واسمح بالإشعارات. على V3H المدعوم يتم اكتشاف خدمة SUNMI واختيار الطابعة 58 مم تلقائيًا. افتح الإعدادات واضغط «طباعة تجريبية». لطابعة خارجية اختر بلوتوث أو شبكة وحدد عنوانها واحفظ. الورقة وحدها لا تؤكد استقبال الطلبات بالخلفية؛ اختبر أيضًا قفل الشاشة وانقطاع النت والعودة.
8. نسخة الاستخدام التجاري تحتاج APK موقّعًا بمفتاح **خاص بتطبيق التاجر** عبر **Generate Signed App Bundle / APK → APK**. احتفظ بالمفتاح خارج Git وبنسخة آمنة؛ لا تستبدل مفتاح تطبيق العميل. يلزم نفس مفتاح التاجر لتحديث هذا التطبيق لاحقًا.
9. عند كل تحديث ارفع `versionCode` في `android/app/build.gradle`، وأعد البناء والتوقيع بالمفتاح نفسه.

## فحوص التطوير

```bash
pnpm run typecheck:libs
pnpm --filter @workspace/basket-merchant run typecheck
pnpm --filter @workspace/basket-merchant run typecheck:server
pnpm --filter @workspace/basket-merchant run test
```

لا تشغل اختبارات قبول/رفض/إرسال رسائل على بيانات المتجر الحقيقي دون إذن.
